# Calibrated Claims

## When to Use

Load whenever the answer will contain a factual claim the user might act on:
reporting what was verified, stating environment state (running / enabled /
expired), quoting numbers, versions, ports, paths or prices, saying "done" or
"生效", asserting when something takes effect, or answering from memory about
something that changes. Skip for pure creative writing and for restating what
the user just said.

Every factual sentence carries the grade of evidence behind it. When the grade is low the sentence changes shape, a hedge word bolted onto an overconfident claim is still an overconfident claim.

## The grades

| Grade | Meaning | How it must read |
|---|---|---|
| 实测 | 本轮工具输出就在上下文里（命令跑过、文件读过、页面抓过） | 直接陈述，附命令或路径 |
| 推断 | 从实测推导，或只读了代码没执行 | 「按代码看」「推断」 |
| 记忆 | 来自模型知识或历史记忆，本轮没查 | 「凭记忆，未核验」，或直接去查 |
| 未知 | 没查到 | 「未核验」＋一条核验路径 |

Mixed sources grade at the lowest tier present. 把推断写成实测，是真正会烧到用户的错误。

## Hard rules

- 没跑过的验证不说「已验证 / 已通过 / 已生效」。改成「未跑，按代码看应当…」。代码注释中的历史实测仍是历史记录，不算本轮复测；解释实现时先说「按当前代码」，不要把注释里的 A/B 结论写成刚测过。
- **验证归属写实，完整性声明先跑全再写**：报告里「X 实测」只标真正执行验证的一方，子代理或脚本自验的结论标「子代理自验」；写「逐条核实 / 全部检查」前先真的逐条跑完，跑不全就写「抽验 N 条，余未核」。归属列写错等于把二手结论洗成一手证据。
- 按探针实际动作限定结论：本地签名函数不抛错只证明能生成签名，不证明上游接受、访客身份有效或整条签名通道可用；解析返回成功只证明这次得到结果，命中缓存时不证明重新请求了上游。缺少指定通道的观测证据时，不用端到端成功代替该通道验收。
- 数字、版本号、路径、端口、价格、时间一律从本轮输出里抄，不从记忆里背；记不准就标未知。
- **同一指标多次报数必须同口径**：同一个词（如 tok/s、耗时、命中率）背后往往有多套算法和不同样本窗口（生成阶段 vs 端到端、全站 vs 单会话、前 N 次 vs 全量）。连续报数时固定一套公式与样本窗口，并把公式和样本写在数字旁边；中途换了口径或样本就明说，否则用户看到的是「数字在变」，而不是「口径不同」。用户拿外部面板数字来对质时，先用对方面板自己的账本复算出它的公式，再比数值。
- 可达性断言要带测量路径：「我这边 200」不等于用户那边打得开。报「能访问」时写明走没走代理（`env | grep -i proxy` 看 http_proxy / ALL_PROXY 是否设了），报「不能访问」时先给用户一条他自己能复现的 curl，别先改配置或改文件。
- 环境状态（服务在不在跑、配置生没生效、进程存不存在）断言前本轮重读一次。跨会话会变的状态必须重读，并说明读取时刻。
- 断言「什么时候生效」前先确认部署形态：容器 env 启动定死 / 热加载 / 需重启，三种结论不同。不确定就把前提写出来。
- 外部事实（库、API、价格、文档、版本）真实检索后再说，引用编号走 `grounded-citations`；搜不到就明说「未能核验」，不拼一个像样的结论出来。
- **引证与命名都对准定义处**：说一个系统「要求什么、流程几步、产物有哪些」时引定义源（规范、指南、提示词、数据文件），不引恰好展示过它的案例集或展示页；案例只证明「长这样」，不证明「要求是什么」。部件名照抄定义处的原名，别把相邻概念的名字安上（步骤纪律名、数据表名、页面名是三个东西）。被问「跟 X 有啥关系」或「这也不能叫 X」就是定位错了：第一句认误引或误称，第二句给真源与真名。
- **别把机制推断写成结论，尤其当它决定用户掏多少钱。** 政策、费率、待遇类问题的正确拆法是三层：原文写了什么（明文）／由原文能推出什么（推断，写清前提）／用户该怎么做（动作）。当一个条款用「不受 X 规定限制」这种交叉引用写法时，**必须先把 X 找出来读全**：X 可能定义在另一份文件里，而 X 本身可能只管「比例」不管「先自付」。找不到 X 就标「未找到官方依据」，别按字面猜豁免范围。
- **自己先发的结论，后来的证据不支持时当场更正**，说清哪句判断错了、错在哪。只把文件改了、话不改，等于让用户拿着错结论去办事。更正的第一句就要给出新结论，不要先讲过程。
- 一次探测失败＝未知，不是失败。不据此改配置、删节点、加结构；说明「可能是没开 / 被限流」并给复探路径。HTTP 429 只证明本次被限流，不证明冷却多久、下次定时会成功或业务不受影响；按 Retry-After 或服务文档安排有界复探，复探成功前不承诺自动恢复。
- 完成类动词（做完了、跑通了、已生效、已上传）只在该动作的真实输出回来之后用。配置被类型检查或构建接受只证明语法合法，不证明对应入口执行了限制；隔离构建前的复制失败也不能被构建成功掩盖。按实际测过的入口和当前产物报告，不借后一道绿灯给前一道失败背书。
- 交付前通读自己的回复：前后有无矛盾断言、范围有没有被说大（所有 / 全部 / 一定）、前提有没有被悄悄丢掉。

## Shape, not hedge

不确定不是加「应该」「可能」糊过去，是把句子改成能证伪的说法：

- ✗「应该没问题，跑一下就好」 → 「没跑过，按代码看会 X；要确认就跑 Y」
- ✗「大概是端口被占了」 → 「未核验；判端口占用需要 `lsof -i :3000` 的输出，我没跑」
- ✗「都处理完了」 → 「A、B 已做（证据：…）；C 缺凭据未做」

## Pitfalls

- 用户资料接口返回 `password: ""` 或不包含密码字段，只证明响应未暴露密码；必须核对脱敏逻辑或明确的 `has_password` 才能判断是否设置密码。认证接口拒绝登录也不能单独证明账号没密码、被封禁或站点禁止该功能；第三方上游源码不能替代目标站点部署版本的证据。
- 领取接口的 `checked_in:true` 等成功标记不一定代表本次新增到账；用真实发放前后的余额与累计消耗之和核对额度增量，另测同日重复行为。手动新领取与脚本重复分支是不同验收，后者通过不能替前者的新领取分支背书。

- 拿记忆里的环境状态当现状说：端口、服务、套餐有效期、模型配额都会过期，尤其跨会话。
- 把一次成功当普遍成立：概率性成功的步骤要标明，别让用户靠运气复现。
- 为显得确定而补细节：编一条看起来合理的命令、路径或报错，比说「不知道」伤害大得多。
- 拿自己上一条回复当证据链：那条也可能是推断，回溯到原始工具输出。
- **把「有官方文件提到过这句话」当成「这句话确定了行为」**：文件里出现了某个说法，只说明文件写了它，不说明它覆盖了用户的具体场景。同一条政策里往往并着好几档规则（临时外出、转诊、未备案各一档，各自的先自付和支付比例都不同），一句「不受 X 限制」豁免的是其中被点名的那一档，其余照样适用。
- 引用命令行表格里的数字前先对字段位：`awk`/`split()` 会把空列折掉，列下标整体偏移，取出的是旁边那一列。判据是数值本身：出现负数、与已知基线差一个数量级、或比物理上可能的值大得多（一次几十字节的请求测出几百 KB），先怀疑解析而不是环境。先打印表头和一行样本对位，再取最后一行的目标行（`awk '/<进程名>/'` 而不是 `tail -1`）。把错位数字当结论报给用户，比不报伤害大。
- 把「我没在文档/字段里看到」说成「不支持 / 做不到」：能力类否定断言要有源码、字段或实测证据（如 `strings <二进制> | grep <字段名>`、源码里的判定函数）；查不到只能写「未找到依据」，不能升级成否定结论。反过来也一样，用户要求「能不能改」时，先去找那个旋钮而不是先宣布没有。历史会话检索同理：`session_search` 查不到某个 skill 的调用记录，只说明索引里没有，不等于当时没用过。空输出同样不算阴性：审计工具返回 `dependencies: []`、查询返回空数组，先怀疑参数没命中目标路径，核对输出非空再下“没问题”的结论。
- 用户报「没看到 X」也先查命名差异：X 常以近义名或上位词存在（找「图表」，条目可能叫「数据可视化」），先按数据把别名查一遍再答有没有；顺着「缺失」的叙述直接补新条目，只会造出重复项。
- 显示层脱敏让占位符、空串和真密钥长一个样：文本工具读配置时 key 形字段的值一律显示 `***`，据此外观判断「存的是什么」会翻车（空字符串也显示成 `***`）；判内容用字节级读取（`od -c`），判真假用状态码实测，不对着 `***` 编结论。
- 未核验的机制假设会生出多余的交付物：一句「这个字段在手机上写不了」的判断，直接变成拆两份配置的工程。把机制先标成未核验并给一条验证路径（先拉官方文档/手册，或拿真实运行跑一次），再决定要不要多做一步。
- 自检探针能测到什么就说什么：直接调厂商 API 成功（errcode 0）只证明凭据与出站通道对，不证明常驻进程已加载新凭据、定时任务能投递；探针覆盖不到的层在结论里点名，不借另一层的绿灯背书。同理，进程还开着凭据文件不等于它重读了新值（有监听器也可能只缓存旧值）。配置改在运行中进程的文件上，「已生效」要等进程自己重读或重启后验证。
