# 项目级意图文件（user-input.md 类）

## When to Use

- 用户要求给项目加一份「用户输入」「项目意图」「这份项目要干什么」的文件，或用户自己改了它，要项目跟上。
- 仓库已有这类文件，需要判断某次改动要不要同步到代码、页面、文档。

## 定位

- 意图文件是需求源，代码 / 页面 / 文档从它派生，不反过来。它不是 README、不是路线图、不是待办清单。
- 位置：仓库根目录；文件名、路径、章节标题照用户给的原样用，不自己换语言版本。
- 体量：≤10 行，每行一句。超了说明在写说明书。只写意图与硬要求，不写实现方案、路径、命令。
- 写法：事实句，不写口号，不写「用户想要……」这类转述。

## 三种触发

1. **新建**：从用户原话、用户亲改的意图文件和已明确采纳的决策提炼目标与验收。README 与代码只用于定位和核对兑现程度，不能充当用户意图来源；未实现的目标仍可保留，不把愿望写成已具备的能力。
2. **用户手改后对齐**（主战场，见下）。
3. **偏差审计**：先区分用户问的是「核心是否表达准确」还是「实现是否兑现意图」。前者对照用户决策，后者对照仓库；只交审阅结果，不擅自修文件或验收业务。流程见下。
4. **对话增量**（默认行为，用户没点名也要做）：用户在对话里说出新的项目级目的、范围或验收口径时，当场写进意图文件，不等用户说「更新一下」。只写项目目的、目标用户、边界、验收口径和明确取舍；一次性执行指令、实现细节、代理自己的推断不写。与旧句冲突时按用户当场的话改写旧句，不叠两套说法；超过 10 行就合并同类、删已被推翻的句子。改动在回复里一行说明。意图变化牵动实现或文档时，走「用户手改后的对齐流程」，或把缺口报出来，不自行扩成待办。

## 用户手改后的对齐流程

1. **先 diff**：把变更拆成三类：被删的条目、新增的硬要求、改写的措辞。用户的版本优先，代理不要用自己的版本盖回去。
2. **逐条落点**：每个变更都要在仓库里找出「还在按旧意图说话」的地方：README 特性段、页面文案、脚本默认参数、生成的产物、文档里的旧数字、验收清单。常见链路是 意图 → 默认 / 配置 → 产物 → 展示，改一层要顺链改完。
3. **区分「降级」与「下线」**：意图删掉一条不等于功能要删。功能仍在仓库里时，判断是降为次要还是下线；下线不可逆，报告给用户拍板，不要自己删。用户已经拍板要下线时，转到 `feature-removal` 技能做全链路删除，不要只改文案。
4. **指路入口**：在主 README（或 VISION / AGENTS）加一行指向意图文件，写明意图与验收以那份为准，让后来者知道权威源在哪。
5. **验证**：新增的硬要求要在实现层找到可测落点，跑一次真实任务确认成立（探活与 mock 不算数）；改过的文档行过标点 gate；产物由脚本生成的，改脚本后重跑脚本，别手改产物。
6. **汇报三段**：改了什么 / 验证到什么程度 / 还剩什么要你做（未决冲突集中列出，不夹带在正文里）。

## 偏差审计流程

1. **锁定对象与范围**：直接读指定文件；多个项目只枚举项目根的意图文件，不递归扫描依赖目录。记录每个项目的路径、正文快照和一句话核心，区分「已有意图文件的项目」与「全部项目」。
2. **按所问取证**：审核心时，先对照用户亲改内容、已记录的明确决策和相关原话，README 只做辅助；核兑现时，再追相关代码、产物或验收记录。不要因校验命令存在就运行它，只有用户要求验证或结论必须依赖执行时才做最小验证。
3. **确认来源与归属**：辨别真正的用户要求、提问、粘贴的助手报告、助手建议和上游告诫。核对请求对象、频率、适用范围及采纳范围，不能把一次询问变成每日任务、把一次公开文稿获批扩大成全部使用约束获批。没有找到采纳证据写「采纳未核验」，不写「用户已拒绝」。
4. **分开判核心与写法**：核心用「吻合 / 明确偏差 / 来源未核验」；另列「文件需收紧」及原因。超行、重复、技术细节和一次性任务不自动等于核心写错。仓库没实现是兑现缺口；较新的助手报告也不能证明用户改了方向。暂停查看、弃用客户端不自动取消项目，旧长期方向是否已拆到别仓需保留归属边界。
5. **有界补证**：缺原话时先列具体缺口，每组默认最多三次针对性历史检索，连续无有效证据就保留未核验并继续其他项，不为证明全部准确穷搜历史。并行任务写明相同范围与调用预算，要求返回来源类型、原消息定位、短引文和未决项；主代理回读支撑明确错项的证据，不能把子代理自述升级成亲自核验。
6. **汇总后交付**：用代码校验项目集合无重复无遗漏，分别统计核心判定与写法问题，不能把「有编辑建议」统计成「核心不准确」。首句回答方向是否准确，正文点出最影响判断的偏差；逐项目证据与建议放一份报告。审计不改项目，不删除未经确认的范围或安全约束。

## 常见坑

- **把一次性任务写成意图**：用户说「把这句改成 X」「跑一下测试」是执行指令，不是意图增量。写进去会挤掉真正的目的与验收，下一轮又被当成需求源照办。判定：换个会话仍然成立、说的是项目要达到什么，才写；只描述这次动作的不写。
- **只改意图文件不动下游**：意图是源，下游断言漂移才是实际后果，用户要的是后者被修好。
- **历史文档里的旧默认值直接改成新值**：带日期的记录保留当时事实，加一行「后续变更」说明当前值以谁为准；活文档（README、页面文案）直接改对。
- **产物当源码改**：产物由脚本生成时，改生成脚本再重跑，然后 `git diff` 确认只动了预期字段。
- **同仓库有并行会话在改**：提交前 `git status` 核对，只暂存自己那几项，别把别人回流的数据文件一起提交；自己那段被别人覆盖时重读再补，不整文件重写。
- **误把其他会话写进 user-input.md 的句子当用户意图**：意图文件的行不都是用户亲写的：并行/别的会话可能凭猜测写入一句（甚至一个砍功能的理由），跟用户当场诉求相反。用户当场的话永远压过文件：出现冲突时按用户改文件，并把顺着那句错话改掉的代码、测试断言一并纠正，别拿「以意图文件为准」去拒绝用户的现场纠正。识别信号：用户说「我早说过要 X / 怎么还是没 X」，而文件写着「不要 X」，信用户。
- **从 git 还原被并行会话删掉的内容别一刀切**：先 `git diff HEAD -- <file>` 双向看：HEAD 有、工作区没了的是被删内容；工作区相对 HEAD 新增的是要保留的改动（如某条 overflow/圆角补丁）。别直接 `git checkout HEAD -- <file>`，会把工作区独有的修复一起冲掉。做法：被删内容用 `git show HEAD:<file>` 取回或只补缺失那段，工作区独有改动保住；还原后 `git diff HEAD` 复核，再跑测试+构建，确认展示层与数据层字段名一致（并行会话常改到一半，两个文件的字段对不上，HEAD 本身可能就是编译不过的半成品，不硬搬，按消费方实际用的字段重建成自洽的一套）。
- **写引用不验证**：意图文件里出现的每个路径写入前用 `search_files (target='files')` 确认存在；并行会话正在改版（目录迁移、删文件）时，指向易变目录的引用改成自包含表述，别留落地即死的深链。
- **把意图写成实现清单**：路径、命令、字段名不进意图文件，那些属于 README 或代码注释。
- **审计范围默认只限用户点名的项目**：用户说「看看这个项目的 user-input 准不准」指他刚提的那个项目，不是 active 目录下全部项目。开工前确认范围；要扩到全量先问一句，别用「顺手多查几个」消耗用户时间与 token。
- **用现状缩小意图**：需求与兑现程度分别记录；实现存在例外时先报告缺口，不把不可妥协的边界改成「尽量做到」，否则审计会替实现降低验收标准。
- **压缩时丢硬要求**：合并同类句子并移出一次性任务，保留用户要求的范围、权限、体验和验收；缓存键等实现细节可移到技术约定，不能连同它保护的用户结果一起删。
- **验收句指向已删产物**：用户新指令下线了某产物、或改了验收口径时，意图文件里指向它的验收句要同批改写；只改过时指代，不替用户改意图，改写后验收句必须落到当前可核对的口径（谁、拿什么核）。

## 边界

- 意图文件 vs 仓库现状的偏差审计走本技能的「偏差审计流程」；其余普通文档与代码的描述对账（漂移审计、勘误 diff）→ `docs-audit`。
- 提示词本身的结构、名额规则、两端口径 → `prompt-optimizer`。
- README 的结构与文风 → `create-readme`。
