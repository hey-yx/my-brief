# 意图变更的下游对齐清单

按需取用，不要整段照抄。每条都带「为什么」，跑之前先确认仓库实际结构。

## 一、定位还在按旧意图说话的地方

用 `search_files` 定位，再用 `read_file` 读命中段，不整仓输出正文：

- 被删功能或约束：`search_files(path=<已确认目录>, pattern="关键词1|关键词2", file_glob=<相关文件类型>)`。
- 旧默认值：在规则、参数、展示各自目录搜索旧数字，读取上下文确认含义，不能把相同数字的无关命中算作漂移。
- 页面自述结构：先确认页面源码位置，再搜索「块|份|步」并核对真实条目，不猜页面在 `app/` 或 `src/`。

关键词取被改条目的名词，不取整句；按相关目录缩小搜索，不扫描依赖与构建产物。

## 二、默认值四层链

改一个默认值（名额、条数、超时、后缀数）时顺着链走一遍，每层都要有落点：

| 层 | 典型位置 | 漏了会怎样 |
|---|---|---|
| 规则层 | 提示词正文 / 配置常量 | 规则仍是旧值 |
| 参数层 | 脚本默认值、CLI 覆盖参数 | 脚本写死数字，规则永远测不到 |
| 产物层 | 脚本跑出的 JSON / 生成文件 | 页面数字与真实批次对不上 |
| 展示层 | README、页面文案、实测记录段 | 读者按旧数字理解 |

参数层的设计：默认值用「不指定 / 留空走规则」这类让规则自己决定的值，别把数字写进脚本；另给一个显式覆盖参数（如 `--count N`）。这样「默认」和「用户明说」两条路径都能各自测。

## 三、产物重建

产物由脚本生成时，顺序固定：改生成脚本 → 跑脚本 → `git diff` 产物文件 → 确认只动了预期字段。生成脚本入口用反查法找：

用 `search_files(path=<项目源码目录>, pattern=<产物文件名>)` 找写出位置，再读入口及调用方。只有授权包含实现对齐时才重建产物，纯核心审阅不执行这一步。

## 四、历史记录加横幅

带日期的记录保留当时事实，文首或相关段旁加一行说明当前值以谁为准：

> 后续变更（同日/次次）：X 从 A 改成 B。文中「A」记的是当时的改动，不是现在的默认值；当前值以 <唯一来源文件> 为准。

活文档（README、页面文案、验收清单）没有这层保护，直接改对。

## 五、验收可测化

把意图文件里的每条硬要求翻成可跑或可核对的断言：

| 意图表述 | 落点 | 断言 |
|---|---|---|
| 默认必须出 N 个 | 规则层默认值 + 参数层不写死 | 跑一次不传参数的调用，断言结果条数 == N |
| 评审不过要再跑一轮 | 规则层补齐回路 | 断言补齐字段记了轮数与补上个数 |
| 不能出现重复 | 规则层避让规则 | 断言结果里主名与配名各自唯一 |
| 查询要给可解释评分与风险清单 | 服务端返回结构 | 断言返回里评分与风险项字段存在且非空 |

要求暂时没有可测落点时，记录验收尚未定义或实现尚未兑现，不据此否定需求。主观质量要求可用用户接受的示例与明确反例对照；不要编一个数值阈值替用户作决定。

## 六、核心与兑现的证据位

先确定审计轴，再取最小证据；目录清理与实现测试不自动属于核心审阅。

| 所问 | 优先证据 | 能下的结论 |
| --- | --- | --- |
| 核心是否表达准确 | 用户亲改文件、原始要求、明确采纳的决策 | 核心吻合、明确偏差或来源未核验 |
| 请求对象或频率是否写错 | 原消息中的对象、动词、频率和上下文 | 仅纠正证据能支持的那一处范围 |
| 当前实现是否兑现 | 相关代码、产物及匹配当前版本的验收记录 | 兑现、缺口或未验证，不能反推意图错误 |
| 一致性是否成立 | 已有记录；需要当前执行证据时才跑校验 | 仅说明该检查覆盖的范围 |
| 优先级是否过时 | 决策原话与采纳链，而非只比文档日期 | 用户后续明确改变方向才判过时 |
| 长期方向是否属于当前仓库 | 项目拆分或职责归属决策 | 未明确归属前不自动加回旧目标 |

区分「内容写错」与「内容放错地方」：旧版号、排障日期、过去的覆盖率可能完全属实，但更适合历史记录；它们不因此成为永久目标。上游安全建议可以保留为来源说明，未找到采纳原话时不能冒称用户决定，也不据此解除现有安全限制。

## 七、批量核心审阅的最小留痕

按项目保存以下字段，不把全部历史正文塞进主上下文：

| 字段 | 用途 |
| --- | --- |
| `project`、`path`、正文快照 | 确定对象并防止跨仓串项 |
| `core`、`core_verdict` | 一句话目的与核心判定 |
| `editing_issues` | 超行、重复、一次性任务和实现细节，独立于核心判定 |
| `evidence_type`、`source_locator`、短引文 | 分辨用户原话、粘贴报告、建议、文档互证和二手摘要 |
| `limitations`、建议 | 记录缺原话、归属待核和未做的运行验证 |

将每组结果追加到工作区 JSON，再聚合核对集合：项目名唯一、总数等于已登记范围、没有缺项或额外项目。分别计数 `core_verdict` 与有 `editing_issues` 的项目，两种数量可以重叠，不能相加或互相替代。

子代理只报消息编号而没有可回读的会话或文件定位时，要求补来源；若预算已用完，标为二手取证，不重新展开整库检索。对明确写错的结论优先回读，其他项保留其实际证据等级。

汇报先答核心方向，再点出具体偏差；详细表留报告。未找到原话不是反证，文档互证也不是用户确认。仅审阅时不修改任何项目文件。
