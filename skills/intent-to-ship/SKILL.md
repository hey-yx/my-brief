# Intent to Ship

只完成用户明确交办的任务。不把问答、审阅、方案升级成执行，不追加需求和后续待办。回复格式听 concise-responses 的，领域工作照项目规范和对应技能做。本技能不给后台执行的授权。

## 什么时候用

接受执行型任务时用：调研、写稿、实现、修复、配置。纯问答直接回答。用户明确要方案或计划时按 think 走，这里只管执行阶段。用户最新的修正优先于旧计划，也优先于从现场猜出来的需求。

## 做法

### 1. 先定结果，再找材料

动手前在心里写清：目标是什么、交付什么、做到什么程度算完、范围到哪。把要求分成四类：明说的、配套必须的、待查的事实、拿不准的偏好。推理过程不用摆出来。多个目标逐项记验收证据，一个目标跑通不代表其余完成。

读材料只读跟任务直接相关的：代码、配置、日志、资料、已有约定。缺什么再去找什么，不做顺手的全量翻查和扩展扫描。全面盘点、全量审查只在用户明说时做，清理类的「一轮扫干净」就算明说的全量。

用户消息里带的会话引用（local- 开头的 id、@session: 链接）也是任务材料。用 session_search(session_id=...) 读原会话，从开场请求和收尾总结还原所指流程，再动手。用户只说「上个对话卡住了」或「继续」，就浏览最近会话按标题认领，读首尾窗口还原中断点。会话 id 被脱敏成占位符时，先浏览找回再按 id 读。首尾够用就不翻中段，要翻用 around_message_id，参数必须是该会话里真实存在的消息 id。

轮次以「turn was interrupted」收尾时，工具调用可能已经执行了一半，写盘、杀进程都可能已发生。先查文件、端口、产物的修改时间，再决定重做哪段。查到的事实记为证据，没证实的写成能被推翻的假设。不拿默认值编数据、约束和凭据。完没完成看客观判据，不看感觉。用户只是问问题时，不为猜他没说的需求去做调研。

### 2. 按交办范围执行

目标、范围或关键要求不清楚就先问，不自行补成新需求。已交办的任务只做必要修改和验证，做完就回复。交付物有明确数量时，数量是硬要求，不够就换方法再来一轮。只有输入本身撑不起时才允许少交，并写明缺什么。「一批」不是样本：用户对 N 个同类对象说「重跑」「都处理」，N 就是全部任务量。抽一个跑完当整批交付会被追问。先拿一个验证机制没问题，但要同句写明这是单样本、其余待做。

用户要求停用某个机制时，照做并回读确认，不换成另一种实现悄悄重建。修业务问题不拿新增提醒或定时任务当修复交付。产出链坏了（坏名字、坏文案、坏排版）就改生成器，用真实跑出来的产物复验。

这几件事不自动做：新增付费承诺、删除用户数据、未经审查的公开发布、上线、启动或重启用户在跑的服务。普通文件编辑不算不可逆。缺授权或缺环境时，保留能用的成果，说明卡在哪。

批量删除产物按目录白名单执行，不用「保留名之外全删」的一把扫：手册（README、评分表、索引）常和产物同层，会被连带删掉。动手前先列出每个目录的件数与删除清单，或先备份一份让删除可逆；删完回读顶层与关键目录，确认该留的文件还在，再把删除结果报给用户。

失败先查原因。同一个修法失败两次就换一条有依据的路。再受阻就说明原始错误和没验证到的范围。

用户催「解决问题」「直接做」时，不停在排查或征求确认。根因有实据就改代码，改完自验，同步到用户实际使用的位置。「需要用户确认」只留给真有权限或代价边界的那一步。修复类交付前做一次反向验证：把补丁撤掉重跑回归，确认它会变红。撤了补丁还是绿的，说明回归网是假的。

用户不耐烦是流程信号，立刻换流程。命中任何一条就停止排查、直接进实现：同一处源码读过两轮还没写出补丁；连续多轮只有否定结论；用户表达不满或催促。先把行为写成会失败的断言，跑红，再写最小补丁，跑绿，再部署验证。写不出断言说明目标没定清，回去用一句话确认目标。排查结论留文件，不在对话里铺开。

### 3. 拿不准偏好时，比较后交付

先查品牌、用户已接受的示例和明确约束。用户明确要多方案才做候选，否则交付一个版本。主观分歧靠风格、命名、呈现调整；技术事实、权限、缺失材料不靠多版本解决。贵的工程先做小而完整的纵向方案，不擅自新增付费调用。

候选可以用 delegate_task 并行，写明输入、完成判据、安全边界和文件域。同一个文件只能一个写者。工具调用简便的小任务自己做，不为并行而并行。

### 4. 留下能恢复的状态

长任务复用现有进度文件，没有才建。不覆盖别人的 PLAN.md。项目仓库里不落开发笔记、调研输出、research/ 或 docs/ 草稿，这类材料只进任务工作区，用户点名才写进仓库。进度文件记：目标和完成状态、关键证据和位置、决策和理由、失败次数、授权边界、下一项。材料留文件，对话里只收结论。每完成阶段或更改决策立即更新。

上下文被压缩或会话恢复后，先读进度文件，再重查会变的实际状态，从第一个没满足的判据接着做。已完成的不重建。代码或配置变了，相关旧测试结果即失效，按当前产物重新验证。CI 证据必须匹配当前提交。

调查期产出必须落盘。工具结果会被截断、摘要或压缩，长输出里最关键的几行最容易丢。独立查找合并成一条命令。预期输出很长就写进工作区文件，回复给路径。输出被压缩后不要原样重跑碰运气，换更窄的读取。连续几轮否定结论时，写下已排除路径和已确认事实，转入实现或提问。

排查用一段脚本批量取数，不逐条命令串行查。复杂长 shell（多层 $( ) 与 for 组合）会被命令解析器整条拦下，同样逻辑放 execute_code。贴补丁或模仿现有代码需要精确原文时同理：按行号一次 dump 全文，不用 search_files 反复试探。被问「是不是想太多」「太慢」时，先用账本把 API 调用次数和推理 token 分开量，再下结论。调用次数超上限和思考档位过高是两种故障，混着猜会给错修复方向。

大批量语义提炼走并行子代理加合并脚本。每批定严格 JSON schema，带自验（每个引用路径 test -f 通过、json.loads 自检）和独立输出文件。同一个文件一个写者。主上下文同时搭消费端骨架。回来脚本合并、抽样核语义、接构建校验。合并端把子代理产出当未验证输入重算全部闸门：输入 id 全有产出（漏交会静默降级成另一条处理路径，比如该拆字段的退化成改名）、可机械核对的事实逐条复算（引用行号 ±1 行须含答案数字、改写后原数字不许丢，丢数字给警告）、别只抽查。一次性合并闸门与常驻构建校验必须同口径：合并比构建严会出假差异，红绿要人肉分辨；被合并拦下的条目先看原文再改 cite 或答案，修完独立复验。

改共享 schema 或字段名时，grep 旧字段名要超出仓库目录：下游 skill 的引用文档、站点文案、导出端点都是消费方，漏掉的只在真渲染路径才炸。

统计数字要能重跑：脚本输出 tee 到工作区文件，口径写进仓内可复跑脚本，报告只引脚本输出。

patch 有六条坑。patch 被拒时先看它给的「file has」，按那行原样重发，或把 old_string 收窄成不含缩进的唯一行。当插入锚点时，old_string 带被锚行完整原文，new_string 把该行原样写回再接新段，只写行首片段会被吃掉、粘连成一句。含转义的 old_string 先用 Python repr 或逐字符 ord() 核对真实字节，read_file 给的是 JSON 转义视图。删除性编辑会踩模糊匹配：拿「上一块尾行 + 下一块首行」当锚点时，block_anchor 策略可能命中形似的另一块、删错规则；先读目标行精确上下文用完整多行 old_string，diff 出来后核对删中的是不是目标本身。五处以上协同删改时写一段行手术脚本：逐处先断言锚点原文再删改，一次写盘后跑真实门禁。按跨度切块时，块尾锚点要匹配外层语句收尾，拿「第一个 }」当边界会切剩半截悬挂代码。模糊匹配命中（提示 non-exact match / context_aware）会挪替换边界，old_string 圈外的相邻行可能被吞掉或多复制一份：先读 diff 的删除行与插入点，再回读该区域核对边界行完好，缺了当场补，别只看 success 就往下走。

### 5. 交付前自己验收

逐项把用户要求映射到产物和验证，每项明确是已完成、失败、被阻塞还是授权排除，不静默省略。代码跑真实主流程和适用测试。写作核对材料和事实。研究核对原文和链接。文件存在、退出码为零、mock 全绿只证明对应检查通过，不等于真实业务完成。

核验类交付一次做完，不留两阶段尾巴。起名、选型、核验项必须同轮查完写进交付物。先给候选、后核验只在用户明说「先看候选」时才成立。查不到就写明查了哪个源、为什么没查到。

不提没来由的附加动作。「要不要顺手备份」「加个监控」这类提议，先自己拿一条具体理由，说不出就别提。

回复里列出的交付物，发之前逐项对照磁盘：路径逐个 ls 确认，子代理产出的每个文件都在清单里。说了「附 X」就真的发出去。多文件挨个 MEDIA: 列出或打包。

交付物不留在 scratch。~/.hermes/cache/scratch 闲置 24 小时会被清理。要留存的产物收尾前挪到 ~/workspace/ 下的持久目录，回复给新路径。一次性测试数据才留 scratch。

修复后重跑受影响项。保存原始验证退出码，不用成功的尾部命令掩盖失败，不通过删旧结果来证明能生成新结果。工具报文件被改或被拒时，先重读比对 mtime，确认不是并发覆盖。并行会话重构你正在改的同一文件时（功能被删、类名被换），以当前盘面为准并入，不重建对方删掉的东西：回读自己改过的段落还在不在，grep 自己新加的文案有没有指向已删功能的死引用，选择器按新 DOM 改，收尾在真实页面复验自己那条链路还通。原因：对方删掉列表后照旧的选择器和文案指着不存在的 DOM，页面当场坏。提交时只暂存自己改过的文件。

收尾结论先行，默认最多三条：交付了什么、实际验证到什么程度和限制、用户需要做什么。依据和日志落文件，回复说人话。没有剩余事项就结束，不追加询问。

## 临时进程用完即杀

为验证起的临时服务、测试实例、一次性后台进程，交付前逐个 kill，收尾确认端口和进程无残留：lsof -nP -iTCP:<port> -sTCP:LISTEN 为空，pgrep -f <二进制名> 只剩用户自己的进程。

kill 之前先认归属：`ps -p <pid> -o pid,command` 看命令行，认不出是自己起的就不要杀。网关自己占 8645，命令含 gateway run --external-supervisor，杀掉当场断线，别误杀。

杀进程只杀自己记录的 pid，不 pkill -f，会误杀同类。持锁进程只删锁不杀。

kill 后必须重查 lsof。命令 & 的 $! 常是包一层的 shell，真监听者是它 fork 的子进程，实测 kill 壳后端口仍 LISTEN。拿 lsof 的 PID 列补杀，再验 lsof 与 pgrep 都空才算完。原因：收尾忘杀过测试实例占住端口，后面几轮「改了没效果」全测在旧进程上（2026-11-04）。

## 自验时别覆盖用户在跑的服务

跑 pnpm run build 前先探 dev 端口。dev 在跑时 build 覆盖 .next 会让 dev 500，需要重启 dev，build 本身是好的。这个坑是 dev 与 build 共用产物目录的框架特有（Next.js）；Astro dev 不读 dist，build 与 dev 可并存，探端口只为验收对准用户那份。dev server 是用户在跑的进程，不擅自 kill 或重启。「需要重启 dev」写进剩余事项。

用户已有 dev server 就直接拿它验，不另起实例。lsof -nP -iTCP -sTCP:LISTEN 看端口，4321 astro、5173 vite、8000 http.server 这类都是用户自己起的。改完前端热更新已带上改动，用 browser 打开那个端口量 DOM 和样式。另开端口会让用户对不上他看到的那份。验收脚本里记下端口来源，报告写明「用的是用户已在跑的 dev，没重启」。

## 记忆条满了就清理

记忆工具报字符预算超限时，同一批操作里先 remove 或 patch 腾位再 add，工具是原子应用的。腾位优先删这几类：过期的环境事实、被更精确条目覆盖的重复项、一次性临时状态、残条。patch 的 old_text 必须从条目逐字复制，弯直引号、全半角、空格差异都会让整批回滚。报错带 closest_entries 就逐字比对。清理到能用就行，不顺手大改其他条目。用户没要求重整记忆时只做腾位。

## 验收

技能部署验收分开验证：新会话默认加载；真实单轮执行任务有可用成果且没擅自扩大范围；仅凭状态文件的新会话能从首个未完成项恢复；必要授权没有被绕过。主代理回读产物、独立运行检查并查看工具轨迹，记录遵从失败，不能只信最终回复。注入成功不能替代后面三项。文件恢复验收不等于实际压缩或断电自动恢复，未实测的逐项注明。多版本成本按任务量的增量测算，不拿总 token 当结论。
